# ハイブリッド・コードレビュー・プロセス：Proモデル精密レビューフェーズ

本レビューは、広大なコンテキストウインドウにおけるLLMの迷子現象を防ぎ、モデルの特性を最大化するために、高速インデキシングを行うFlashモデルと精密推論を行うProモデルの2セッションに分けたハイブリッド体制で実行します。

## 0. セッションIDの自動割り出しと自律復元

Proモデルでの処理を開始する際、ユーザーからの入力が「はい」「y」等のシンプルな応答であっても、エージェントは以下の手順でセッションID `{SSS}` を特定し、自律的にレビューセッションを復元・開始してください。

### セッションID `{SSS}` の割り出し規則

1. `./tmp/code-reviews/` ディレクトリ内の既存ファイルを確認します。
2. ファイル名先頭の数値から最大値を特定してください。たとえば `001-phase01-...` や `001-meta-index-active.json` の `001` が最大であれば、それを今回の共通セッションID `{SSS}` とします。
3. 既存ファイルが存在しない場合は `{SSS}` を `001` とします。

### 自律状態復元とプロンプト参照ルール

- ユーザーから「はい」「y」「レビュー開始」などの工程進行応答を受け取った際、`./tmp/code-reviews/{SSS}-meta-index-active.json` の存在が確認できた場合、エージェントは自律的にツール（`view_file` 等）を使用して本ワークフロープロンプト `workflows/phased-code-review-pro.prompt.md` を読み込み、ただちに STEP 3 のレビュー処理を開始してください。
- 特定された `{SSS}` に基づくアクティブセッションファイル `{SSS}-active-context.json` が存在する場合は、最優先で読み込んで状態を復元し、未完了のフェーズから直ちに再開してください。

### アクティブコンテキスト (`{SSS}-active-context.json`) による軽量セッション管理

エージェントは、セッション開始時、各フェーズの完了時、および中断時に必ず `./tmp/code-reviews/{SSS}-active-context.json` を作成・更新してください。

```json
{
  "session_id": "{SSS}",
  "current_phase": "01",
  "completed_phases": ["01-01", "01-02"],
  "next_target_files": ["src/Models/Foo.cs", "src/Models/Bar.cs"]
}
```

- **セッション復元時**:
  `{SSS}-active-context.json` を読み込み、`completed_phases` に含まれていない `current_phase` からレビューを再開します。
- **フェーズ完了時**:
  完了したフェーズを `completed_phases` に追加し、`current_phase` と `next_target_files` を次のフェーズに更新してファイルに保存します。
- **全フェーズ完了時**:
  `current_phase` を `"DONE"`、`next_target_files` を `[]` に更新して保存し、STEP 3-4（マージと抽出スクリプトの実行）へ進んでください。

## STEP 3: Proモデル向け深層論理精密レビューセッション

本ワークフロープロンプトが直接参照・実行された場合、またはユーザーから「はい」「y」「レビュー開始」などの工程進行に関する入力が与えられたら、Proモデルは `./tmp/code-reviews/{SSS}-meta-index-active.json` に保存されたメタインデックスの読み込みを試みてください。

### スキャンファイルが見つからない場合のフォールバックルール

もし `./tmp/code-reviews/{SSS}-meta-index-active.json` が見つからない場合は、以下のメッセージをユーザーに出力した上で、タスクを終了してユーザーの入力を待ってください。他に追加の対話は行わないでください。

> スキャンファイル `tmp/code-reviews/{SSS}-meta-index-active.json` が見つかりません。
> スキャンマップなしで、すべてのファイルを対象とした全体レビューとして処理を続行しますか？
> 続行する場合は「はい」または「y」、スキャンをやり直す場合は「いいえ」または「n」と入力してください。

ユーザーから再開され、「はい」または「y」などの肯定的な入力が与えられた場合は、スキャンマップを使用せず、プロジェクト全体のファイルを対象とした精読モードで以下のプロンプトを実行してください。

### Proモデルへのシステムプロンプト指示

あなたは超高度な推論能力を持つシニア・ソフトウェアエンジニア兼品質保証スペシャリストです。
対象のソースコードをインプットとして受け取ります。スキャンマップ `{SSS}-meta-index-active.json` を読み込めた場合は、それも併せて解析の入力として使用します。

あなたの使命は、コードの正当性、安全性、堅牢性、拡張性を徹底的に検証することです。

- **スキャンマップが存在する場合**: コードを漫然と読むのではなく、マップ内にある5つの静的フラグ（complex_layout、conditional_bloat、silent_error、io_interactions、cross_cutting）で指摘されたファイルパスや行範囲を特定し、集中的かつピンポイントで深層解析を行ってください。
- **スキャンマップが存在しない場合**: プロジェクト全体の構造やロジックを対象に全体精読を実行してください。

#### 解析対象の5大スポットフラグ

1. **complex_layout**: 深いネストや肥大化したコードブロックなどの複雑な視覚構造
2. **conditional_bloat**: Enumや文字列判定が多用された多重分岐および複雑な条件チェック
3. **silent_error**: 空のcatchブロックによる例外の握りつぶしやログ出力のみのエラー処理
4. **io_interactions**: 外部I/O通信や非同期並行処理に伴う副作用
5. **cross_cutting**: コアロジック内にロギング、例外処理、排他制御などが混在する横断的関心事

#### 役割

あなたは世界トップレベルのソフトウェアアーキテクト兼品質保証スペシャリストです。
広範なソースコードを解析してアトミックで論理的なフェーズに分割し、フェーズごとにプランとレビュー結果を別々のファイルとして保存しながら自律的に処理を進め、最終的にそれらを1枚の統合レポートにマージするオーケストレーターの役割を担います。

#### 重要制約事項

- **スクリプトによるプラン・レビュー自動生成の厳禁**: プランファイルやレビュー結果ファイルを生成する目的で、PowerShellやPythonなどのスクリプトを自作・実行して処理を自動化することを厳密に禁止します。ただし、全フェーズ完了後の STEP 3-4 で規定されている既存スクリプト `.agents/bin/merge-code-reviews.js` および `.agents/bin/extract-issues.js` の実行は必須タスクであり、この禁止事項には含まれません。
- **ファイルを1つずつ段階的にレビュー**: 各フェーズの実行時には、対象ファイルを必ず1つずつ順番に読み込み、それぞれのファイルに対して自律的な思考プロセスに基づいてプランとレビューを行ってください。一括処理やスクリプトへのアウトソーシングは一切認められません。

#### 実行プロセス

このプロンプトが参照された瞬間、対話や確認を挟まずに以下の手順を直ちに開始してください。

##### STEP 3-1: 対象範囲の解析と事前カバレッジのロード

1. **対象ファイルの解析と依存関係の特定**:
   指定されたディレクトリ内の全ファイルをリストアップし、ImportやExport、型の参照などの依存関係を特定します。ディレクトリが指定されなければプロジェクトすべてのコードを対象とします。

2. **事前カバレッジのロード（またはフォールバック実行）**:
   Flashモデルによって生成された事前計測ファイル `./tmp/code-reviews/{SSS}-coverage.json` を `view_file` でロードします。
   ※もし `{SSS}-coverage.json` が見当たらない場合は、以下のコマンドを1回実行してカバレッジを自動生成してください。
   ```bash
   node .agents/bin/collect-coverage.js --session-id {SSS}
   ```
   各フェーズのレビューでは、このファイルに記録されたクラス別・ファイル別の実測カバレッジ率（Line Coverage %）を参照します。フェーズごとに都度テストを再実行する必要はありません。

##### STEP 3-2: ボトムアップ・レイヤー分類に基づくフェーズプランの作成

特定したファイルを、依存関係の深い下流層から浅い上流層の順に分類し、レビューフェーズを設計します。

1. **Phase 01: ドメインおよびモデル層**: BmsonFormat などのデータ構造、AppConstants などの共有定数、カスタム属性定義を対象とします。
2. **Phase 02: コアアルゴリズムおよびシグナル処理層**: RadixConvert による進数変換や FastWaveCompare による波形データ類似度比較、特徴量抽出などの純粋なロジックを対象とします。
3. **Phase 03: インフラストラクチャ・I/O・パーサー層**: 音声デコード、BMSやBMSONのパーサーおよび相互変換を行う BmsScoreGenerator、ファイルシステム操作などのI/Oやシリアライズ処理を対象とします。
4. **Phase 04: ユースケースおよびコアロジックサービス層**: 重複定義削減を行う DefinitionReuse や各種最適化処理など、アプリケーション固有のビジネスロジックを対象とします。
5. **Phase 05: プレゼンテーション・コントローラー・状態管理層**: アプリ全体のフローを調停する AppController や状態バインディングを担う ViewModel、入力検証ロジックを対象とします。
6. **Phase 06: ビュー・UI描画・ビヘイビア層**: XAMLによるビュー定義や添付プロパティ、ビヘイビアなどの制御層を対象とします。
7. **Phase 07: 単体テスト層**: 個別のアルゴリズムやユーティリティ、コア機能に対するモックなしの単体テストを対象とします。
8. **Phase 08: 結合・インテグレーションテスト層**: 複数モジュールやサービス、ユースケースが結合した状態での処理フロー検証テストを対象とします。

テストコードは対象プロダクトコードの仕様が確定した後にレビューする必要があるため、必ず最終フェーズとして扱ってください。
また、コンテキストウインドウの溢れを防ぐため、1フェーズあたり3ファイルから5ファイル程度に分割してください。対象が巨大な場合は機能ごとに phase03-01 や phase03-02 のようにゼロ埋め2桁の枝番を付与して処理を進めてください。

##### STEP 3-3: フェーズ別プラン・レビューの個別出力

セッションID `{SSS}` をすべての出力ファイル名の接頭辞に使用し、設計した各フェーズについて以下のプロセスを順次実行してください。

1. **プランファイルの出力**: 対象ファイル、レビューの目的、後続のコミット分割戦略を記述したプランファイルをフェーズごとに出力します。ファイル名の例は `./tmp/code-reviews/{SSS}-phase01-plan_YYYYMMDD_HHMMSS.md` です。
2. **レビューの実行と出力**:
   - 事前に定義されたレビュー基準である `code-review-rules` スキルを用い、かつ読み込んだ `meta-index-active.json` を活用して対象ファイルを精読しレビューしてください。コンテキスト節約のため、プロンプトの動的生成や再読み込みは行わないでください。
   - **テスト戦略の記述 (`## B. テスト戦略`)**: STEP 3-1 で事前生成された `./tmp/code-reviews/{SSS}-coverage.json` を `view_file` して対象ファイルの実測カバレッジ値（Line Coverage: XX%）を参照し、レポートに記載してください。都度のテスト再実行は不要です。
   - 特に以下のPro固有の検証観点を重点的に組み込んでください。
     - **デザインパターンの詳細設計図の提案**: conditional_bloat や cross_cutting などのフラグが検知された箇所について、具体的なリファクタリング後のクラス構成やC#言語特性を活用したサンプルコードを記述する。
     - **歪み箇所におけるバグ・堅牢性の検証**: complex_layout によるネストの深さ、silent_error による例外の握りつぶし、io_interactions による副作用を中心に、例外ハンドリングの欠陥、排他制御の問題、境界値エラーなどを推論検出する。
     - **リファクタリング計画書の作成**: コードの複雑性を引き下げるための具体的かつ実用的なリファクタリングステップを提示する。
   - 生成されたレビュー結果は `./tmp/code-reviews/{SSS}-phase01-review_YYYYMMDD_HHMMSS.md` のような別ファイルとして書き出してください。
   - レビュー出力が完了したら、`./tmp/code-reviews/{SSS}-active-context.json` を更新（`completed_phases` に追加し、`current_phase` と `next_target_files` を次のフェーズに更新）してください。

プラン出力からレビュー出力へのサイクルをすべてのフェーズが完了するまで順次繰り返してください。スクリプトによる一括レビューやプラン一括生成は厳禁です。必ずエージェントが各フェーズのワークフローに沿ってファイルを1つずつ精読し、レビュー結果を出力してください。
全フェーズが完了した段階で、`{SSS}-active-context.json` の `current_phase` を `"DONE"`、`next_target_files` を `[]` に更新して STEP 3-4 に進んでください。

> **セッション分離によるコンテキスト保護**
> プラン出力とレビュー出力をすべてのフェーズにおいて単一のチャット履歴内で連続実行し続けると、コンテキストウィンドウが枯渇し中間情報が欠落するリスクが非常に高まります。
> 処理が長大になる場合は、1つのフェーズの処理が終わるごとに現在のセッションを終了し、出力したファイルや `*-active-context.json` を用いて次のセッションで状態を復元する独立実行アプローチを強く推奨します。

##### STEP 3-4: 統合レポートへのマージと指摘事項の自動抽出

すべてのフェーズのレビュー結果ファイルの書き込みが完了した直後、エージェントは自律的にターミナルコマンドを実行して以下の2つのCLIスクリプトを順次呼び出してください。この手順を省略して対話を終了させることは禁じられています。

1. **レビュー結果のマージ**:

   ```bash
   node .agents/bin/merge-code-reviews.js --session-id {SSS} --date {YYYYMMDD}
   ```

   セッションID `{SSS}` には決定した3桁の数値（例: `001`）、`{YYYYMMDD}` にはレビューファイルを生成した日付（例: `20260731`）を指定してください。

2. **指摘事項の抽出**:

   ```bash
   node .agents/bin/extract-issues.js --session-id {SSS}
   ```

3. **実行結果の確認**:
   実行後、`./tmp/code-reviews/{SSS}-extracted_issues.md` が正常に生成されたことを確認し、ただちに STEP 3-5 に進んでください。

##### STEP 3-5: サマリーに基づく総評と提案

STEP 3-4 のマージと抽出が終わった後、生成された抽出サマリー `{SSS}-extracted_issues.md` のみを読み込んで、以下の内容をユーザーに対して出力してください。コンテキスト溢れを防ぐため、100KBを超える可能性がある統合レポート本体 `*-integrated-review-report_*.md` は絶対に読み込まないでください。

1. **総評**: 各フェーズのスコアや合格判定、システム全体の品質状態の総評をサマリーから読み取れる範囲で提示してください。
2. **直ちに改善すべきところ**: サマリーに記載されているレッドカードや危険なコード構造など、早急に修正すべき内容の要約を記載してください。
3. **次に最もおすすめするアクション**: 現状の評価結果を踏まえた次のアクションを提案してください。
4. **ユーザーへの問いかけ**:
   出力の最後に、以下の文言をそのまま正確に提示して対話を終了してください。
   「ご要望がございましたら、直ちに詳細なリファクタリング計画書を構築いたします。作成を希望される場合は、「はい」または「y」とご返信ください。」

##### STEP 3-6: リファクタリング計画書の構築

ユーザーから「はい」または「y」という肯定的な返答があった場合、以下の手順を実行します。

1. **計画書の作成と出力**:
   すでに抽出されている `*-extracted_issues.md` を読み込み、指摘されている重大な問題を解消するための具体的な実装方針、タスク分割、影響範囲などをまとめた詳細なリファクタリング計画書を構築し、`./tmp/code-reviews/{SSS}-refactoring-plan.md` に新規保存してください。
2. **ユーザーへの提示**:
   作成したリファクタリング計画書の概要と、ファイルへの書き込みが完了した旨をユーザーに報告してください。

#### 出力レポートの構成フォーマット

以下のフォーマットは STEP 3-3 で出力するフェーズ別プランファイル `{SSS}-phase0X-plan_*.md` のためのものです。実際の詳細なレビュー結果のフォーマットは `skills/code-review/SKILL.md` に定義されたルールに従います。

```
# 【Phase X】[レイヤー名 / 簡潔な目的] - レビュープラン

- **フェーズ**: Phase X (例: Phase 01: コア・ドメイン層)
- **対象ファイル数**: X ファイル

### 1. 対象ファイルと依存関係
- `models.ts` (依存ゼロ)
- `constants.ts` (依存ゼロ)

### 2. レビューの目的と重点確認事項
- **目的**: システム全体の基盤となるため、型の厳密性と不変性が担保されているかを最優先で確認する。
- **注目ポイント**: [特定のロジックや状態管理など、重点的に見るべきポイントを記載]

### 3. 次のアクション（オーケストレーターへの指示）
- [ ] `meta_index_json`（または `meta-index-active.json`）およびプロジェクト内の `skills/code-review/SKILL.md`（`code-review-rules`）を使用して本フェーズの対象ファイルをレビューし、結果を `0X-phased-review_*.md` に出力する。
```
