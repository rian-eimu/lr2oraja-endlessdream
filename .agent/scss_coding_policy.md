# SCSS Design Policy: Semantic Modifier Chaining

当プロジェクトでは、SCSSのネストに関して「階層の深さ」という数値的な基準よりも、**「意味的な連鎖（Semantic Chaining）」**という設計思想を最優先します。

## 1. 核心となる思想：HTMLとCSSの共生

私たちは、HTMLの`class`属性を、単一の識別子（BEMの`--modifier`）の置き場としてではなく、**「エンティティの状態を合成する場」**と定義しています。

- **マルチクラスの許容**: `.btn.is-primary.is-loading` のような記述は、ボタンという「存在」に「主要」と「読込中」という「状態」を掛け合わせています。
- **メリット**: 状態の組み合わせ爆発を防ぎ、HTMLを見ただけでその要素の現在のコンテキスト（文脈）を理解できます。

## 2. ネストの評価基準 (Depth vs. Chain)

AIエージェントは、ネストを検出した際に以下の「性質の差」を厳格に区別してください。

### A. 連結（Chain）: **維持・推奨**

同一要素に対するクラス連結（`&.modifier`）や擬似クラス（`&:hover`）は、深さにカウントしません。これらは「要素の定義の一部」です。

```
.action-card {
  &.is-selected { // 状態1
    &.has-error { // 状態2
      border-color: var(--bs-danger);
    }
  }
}

```

### B. 子孫（Descendant）: **リファクタ対象**

異なる要素間の構造的なネスト（`.a .b .c .d`）が4階層以上続く場合は、メンテナンス性低下のサインと見なし、リファクタリングを提案してください。

```
// 避けるべき例（子孫セレクタの乱用）
.instructions {
  .step {
    .content {
      h3 { ... } // 構造の依存が強すぎる
    }
  }
}

```

## 3. AIへのリファクタリング・プロトコル

AIは `agency_gatekeeper.ps1` の結果を解釈する際、以下のロジックで行動してください。

1. **判定**: 検出されたネストは `&.` で始まっているか？
   - **Yes**: そのまま維持。むしろ、状態の組み合わせが整理されているかを確認。
   - **No**: 子孫セレクタである場合、その「構造の必然性」を疑う。
2. **提案**: 子孫ネストを解消する場合、新しい「Block」として独立させるか、共通のMixinに抽出することを検討せよ。

## 4. なぜ「BEM」を盲信しないのか (The Why)

`.block--modifier--state` のような長く複雑なクラス名は、HTMLの可読性を損ない、スタイルの再利用性を下げます。私たちは**「CSSの結合子（Combinators）」を正しく使うことこそが、最もモダンでセマンティックなCSS設計である**と信じています。
